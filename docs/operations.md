# 运维：Actions、部署与错误处理

> 描述 GitHub Actions 工作流、Pages 部署、错误处理策略与待观察问题。
> 工作流入参/矩阵细节以 `.github/workflows/*.yml` 为准；退出码定义以 `run.py` 为准。
> cron 全部避开整点（官方文档明言整点是高负载时刻，调度会被推迟甚至丢弃）。

## 定时与工作流

**公开仓库 + GitHub Pages**（免费账号 Actions 分钟数无限；私有仓库要 Pro 才能发 Pages）。
key 放 repository secret `ITAD_API_KEY`，用环境变量注入。

| 工作流 | cron（UTC / 北京） | 作用 |
| --- | --- | --- |
| `daily.yml` 主跑 | `14 19` / 03:14 | 全流程 + 报表发布 + data 回写 + 告警 |
| `daily.yml` 补跑 | `21 21` / 05:21 | `daily-guard` 检测过去 12 小时内已有成功的**定时**主跑则跳过（⚠️ 不能按「UTC 当天」过滤——主跑可能创建于 UTC 前一天；guard 只数 `--event schedule`，不计手动运行） |
| `daily.yml` 预抓 | `14 7` / 15:14 | `--prefetch`：纯 state 派生补欠账，不出报表；价值 = 到期窗口条目提前 ~12h 刷新供次日快照/报表 |
| `daily.yml` 孤儿清理 | `14 7 2` / 每月 2 日 14:14 | data 分支孤立分支清理 |
| `backfill.yml` | 手动 | 通用回填入口：`script` / `args` 两个入参选定 `tools/backfill_*.py`（史低期 / Steam 封面 / 小黑盒中文名），统一注入 config + `ITAD_API_KEY` |
| `probe.yml` | 手动 | 探针（有闸、零常驻成本） |
| `checks.yml` | 手动/PR | 提交前校验 |

> GitHub 调度器偶发延迟（实测最大 8h46m）甚至直接丢弃定时触发（无 run 记录）。
> 补跑被 guard 的 12h 窗口跳过**不是缺陷是设计**：主跑成功了，补跑自然该跳。
> 延迟送达的主跑与补跑并发时，优先用本地 `run.py --prefetch` 补预抓
> （手动 workflow_dispatch 会让两 job 同 run 并行写 data 分支，fetch first 会拒）。

### S8 工作流加固要点

- **timeout-minutes**：主跑 90 · 预抓 60 · guard 5 · 清理 10 · 告警 5
- **失败自动开 Issue**：`alert` job 监听各 job failure（cancelled 不告警，有意），
  正文附 run.py 退出码。退出码口径：`0` 成功 · `1` 未预期 · `2` 配置 ·
  `3` 滥用封禁 · `4` 请求失败（**仅报表产出前**，页面没更新）·
  `5` 详情/覆盖阶段失败（页面已兜底发布首版，欠账下轮自愈）——
  4/5 的判别轴是「页面是否兜底」。同日同因标题去重
- **`$GITHUB_STEP_SUMMARY`**：每轮一张关键指标表 + 阶段墙钟（`run.py` 的 StageClock 写入）
- **报表发布韧性**：「打包报表 / 发布 Pages」`if: !cancelled()` + `hashFiles` 兜底——
  退出码 5 时首版报表照常发布，页面永远可见；手动取消 / 超时连带取消时不发布半成品；
  失败 run 不计 guard 的「成功定时 daily」，补跑照常重试。状态回写用 `always()`：
  取消场景下已抓一半的状态写回去，下一轮断点续传受益
- **permissions 按 job 最小化**（顶层清零）；data 回写 push 前 `git pull --rebase`
- daily/prefetch 的状态恢复与回写抽成 `.github/actions/{state-restore,data-writeback}`
- actions 全升当前主版本；`ubuntu-latest` 维持（观察 runner 渐进迁移 Ubuntu 26.04 的首跑）

### 三个必须处理的坑（都来自官方文档核实）

1. **`GITHUB_TOKEN` 推送的 commit 不会触发 Pages 构建**（官方防递归）
   → 发布**必须**用 `actions/deploy-pages` 在**同一次运行内**完成
2. **公开仓库 60 天无活动会禁用定时任务** → 每日提交状态文件正好算作仓库活动，顺带规避
3. **Actions runner 无持久磁盘** → 靠 `GITHUB_TOKEN` 把状态 JSON 提交回仓库
   （`actions/cache` 有 7 天淘汰规则、官方明确不能当可靠存储；artifact 只留 90 天）

### `.gitignore` 的坑

**现行方案**：main 分支的 `.gitignore` 直接写 `data/` 即可 —— 状态库由独立的
data 分支持有，main 不留 `state.json`，无需在 main 保留任何 `data/` 内容。

**历史坑**（只在「状态留 main」的旧方案里适用，若回退到该方案必须避开）：
想在 `data/` 下保留 `state.json`，**不能**写 `data/` 再配 `!data/state.json`，
必须写 `data/*` + `!data/state.json`。实测（临时仓库 `git add -A --dry-run`）：
写 `data/` 时 git 根本不进入该目录，后面的 `!` 取反无效，`data/state.json`
**被静默跳过**。后果非常隐蔽：**本地跑完全正常**，只有 Actions 上每轮都从空状态
开始（详情缓存全失效、TTL 形同虚设），「每日提交算仓库活动」也一起失效。

### Pages 缓存

约 10 分钟缓存，**且不支持自定义响应头**
→ 资源加 `?v=<生成时间戳>`，页面内显示生成时间以便区分新旧。

### 失败告警（两层）

1. GitHub 通知设置里开启 Actions 的「仅失败时通知」（用户级设置，不用改 workflow），
   失败自动开 Issue
2. 页面内建**数据陈旧横幅**——即使通知被忽略，一打开页面就知道数据是旧的

## 错误处理

- **五种响应分开处理**（不能都当成"限流"）：

  | 响应 | 处理 |
  | --- | --- |
  | `429` | 尊重 `Retry-After`；没有则从 10 秒起退避，逐步加到分钟级；同时**自动降速** |
  | `403` | 比 429 严重（滥用封禁）。等 5 分钟后重试；**连续出现则中止本轮并告警** |
  | `200` 但 body 是字面量 `null` | 软限流。按限流处理，**绝不能当成"没数据"** |
  | `200` 且 `success: false` | 不是限流：appid 不存在 / 该区不售。记 run_log 后跳过 |
  | `503` | 服务端故障，与限流无关。重试，**不计入限流统计** |

- **绝不轮换 IP 规避限流**（社区明确不建议，长期会导致密钥/IP 封禁）
- **退避重试**：5xx 指数退避 + 抖动；网络异常重试 3 次
- **墙钟预算**：同一轮所有传输客户端共享 `http_budget_seconds`，到点主动中止
  （走退出码 5 + 首版报表兜底 + 下一轮自愈），避免被 job 的 `timeout-minutes` 硬杀；
  `Retry-After` 等待时间封顶 300 秒，避免大促期间主跑被提前中止
- **断点续传 / 部分失败不阻断 / 幂等 / 异常数据如实记录**：见
  [pipeline.md](pipeline.md) 的「设计不变量」
- **汇率源挂了不让整轮失败**：沿用缓存旧值并告警（见 [data-sources.md](data-sources.md)）

## 待观察清单

> 记「已知但**暂不处理**」的问题。每条写清：现象 → 为什么现在不处理 → 什么信号出现时回头处理。

1. **点大卡定位在「平史低补位」上可能找不到**：「新史低」板块只收新史低，
   而大卡在新史低不足一页时会用平史低补位——这类卡不在该板块，点它会退到「全部折扣」
   再定位，定位的自动加载上限是 1500 行（`app.js` 的 `LOCATE_MAX`），超出定位不到。
   **暂不处理**（两条件互斥）：新史低不足一页 = 非大促 = 全部折扣总量也就几百条，
   1500 够用；大促时新史低撑满 → 不用补位。**回头处理的信号**：非大促日「全部折扣」
   总量明显超 1500，或用户反馈点大卡找不到 → 改用**弹窗**看详情。
2. **冷启动期新史低的「间隔」大面积为空**：间隔来自史低期记忆 `low_period.prev`，
   需该游戏至少经历两段史低期才攒得出。**观察**：随史低期轮转（每周四北京 01:00 换档）
   覆盖率是否渐进上升。
3. **回填只覆盖 quality / notable**：回填按 `classify.tier_of` 判档，而「详情待补」
   （pending 是抓取状态不是评档结果）的条目回填时被跳过。**自愈**：详情补齐后重跑回填
   即覆盖（脚本幂等、只填空不覆盖）。**观察**：回填后数日 prev 覆盖率。
4. **仓库外 UI 权威 `refs.md` 与现行大卡口径冲突**：refs §10.2 仍写大卡「名气优先 /
   间隔 15」，与 2026-10-09 裁决的「折扣优先 / 间隔 10」不一致。代码与 docs 已按裁决走，
   refs 未改（仓库外、用户维护）。**待用户决定**是否在 refs 补裁决记录。
5. **好评阈值与分档阈值的真实比例**：样本偏热门，靠 run_log 记录的各档条数回调；
   `notable_review_count = 10000` 是从 3 个样本推的。**信号**：run_log 中
   「高热度」档长期为 0 或占比异常时复核。
