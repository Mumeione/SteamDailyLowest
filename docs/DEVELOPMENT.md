## 1. 项目目标

每天定时抓取 Steam 折扣，筛出**处于历史最低价**的游戏，生成一个公开的静态网页，
按「当日新增 / 本周 / 折扣中 / 即将过期」筛选浏览，手机和 PC 都能舒服地看。
（原先还有「已过期」，已删除 —— 见 §4.6。）

核心诉求（按优先级）：

1. 只看**史低**，非史低的普通折扣不进列表
2. 突出**当日新增**——这是每天真正要看的东西
3. 手机可看，多人可看（不只是自己）
4. 全程自动化，跑挂了要能发现

**明确不做**：价格提醒/推送、Steam 账号与愿望单同步、非 Steam 商店的独立列表、价格走势图。

### 1.1 视图上线范围

> 2026-09-27 更新：**「即将过期」已上线**（批 H）。
> 2026-10-05 更新（重构 S5）：**「本周 / 折扣中 / 全部」已上线** —— 数据走独立的
> `all.js` 懒加载（今日筛选链全量，服务端预打视图成员标志），
> 「全部」沿用分组 + 筛选交互；「当日新增」改为**扁平精选列表**（分层字典序：
> 新史低 → 折扣力度 → 评价数，好评达标/高热度降级为卡片标签）。
>
> 2026-10-07（S9 UI 重做）：**视图切换界面作废** —— 改为**首页四板块**
> （新史低 / 即将到期 / 热门游戏 / 大额折扣，见 §7）+ 导航栏「全部折扣」；
> 数据仍走 `all.js` 懒加载。
> 2026-10-08（首屏修复）：`data.js` 不再写 `groups` / `view_groups`
> （大促尾期「即将过期」≈ 全池，曾把 `data.js` 撑到 7.4MB），分组卡片只在 `all.js`；
> 无前端消费者的视图按钮组（`VIEWS` / `payload["views"]` / `upcoming_items`）一并删除；
> `app.js` 懒加载 `all.js` 带上 `?v=`（防 Pages 缓存）。
> 2026-10-08（第二轮，分类页修复）：**单文件 `all.js` 下线**，改按板块顺序切成
> `all/<板块>_<片号>.js`（每片 200 条，首片 gzip ≈ 20KB，降幅 97%）—— 分类页
> 20 秒的病根是「一次性全量阻塞」，不是 GitHub 网络。顺序 = 分片的物理顺序，
> 故 `section_order` 不再单独下发；第 0 片带预聚合计数表 `agg`（5×160 个筛选组合），
> 只加载一片也能给出精确的「共 N 条」。首页空闲时用 `requestIdleCallback` 串行
> 预取五个板块的第 0 片（≈100KB），点进分类近乎瞬开。详见 §7.3.1。

「攒库」策略保留下来的两个好处：

- 「详情待补」在大促首日就不会影响观感——因为详情优先抓的是当日新增，那正是核心视图
- 详情与好评率随运行**自然越攒越全**，等以后开放其余视图时，库里的数据已经相当完整，
  不需要专门做一次昂贵的全量回填

§3.5 的好评分档对**每个已上线视图独立生效**（同一套管线分别跑当日新增与即将过期候选）。
状态库从一开始就按完整结构写（见 §5），不做简化版，避免以后迁移。

## 2. 数据源

### 2.1 ITAD（主数据源）

`https://api.isthereanydeal.com`，需 API key。限额 **1000 请求 / 5 分钟**（需验证邮箱），
超限返回 429 并带 `Retry-After`，必须实现退避。

key 存放：本机 `config.json`（已 gitignore）；GitHub Actions 用 repository secret
注入环境变量 `ITAD_API_KEY`。**任何情况下不得写入入库文件。**

#### 用到的端点

| 端点                                | 用途                  | 成本              |
| --------------------------------- | ------------------- | --------------- |
| `GET /deals/v2`                   | 抓折扣列表（**主接口，一个就够**） | 每 200 条 1 次     |
| `GET /games/info/v2?id=<uuid>`    | 取 `appid` + 好评率     | **一游戏一请求，无法批量** |
| `GET /games/history/v2?id=<uuid>` | 价格历史（本方案只在诊断时用）     | 一游戏一请求          |

#### `GET /deals/v2` 参数

`country`（国家级）、`shops`（Steam = **61**）、`limit`（≤200）、`offset`、
`sort`（如 `-cut`）、`filter`。分页靠返回的 `nextOffset` + `hasMore`。

#### ✅ 返回结构（实测）

每个 item 内嵌完整 `deal` 对象，**不需要再调其它接口补价格**：

```
item:  id(ITAD uuid) / slug / title / type / mature / assets.boxart…banner600 / deal{}
deal:  shop{id:61,name:"Steam"} / price / regular / cut / voucher
       storeLow / historyLow / historyLow_1y / historyLow_3m
       flag / drm / platforms / timestamp / expiry / url
```

#### ✅ 字段语义（官方文档没写，实测反推）

| 字段                           | 含义                               |
| ---------------------------- | -------------------------------- |
| `deal.storeLow`              | **该商店（Steam）历史最低价，且已把当前这次折扣算进去** |
| `deal.historyLow`            | **全商店**口径历史最低（全周期）               |
| `deal.historyLow_1y` / `_3m` | 全商店口径的近一年 / 近三月最低                |
| `deal.flag`                  | **官方的新史低/平史低标记，直接套用**，见下表        |
| `deal.timestamp`             | 本次折扣**开始**时间                     |
| `deal.expiry`                | 本次折扣**结束**时间                     |

#### ✅ `flag` 取值表（本项目的核心判定依据）

| flag   | 含义                        | 验证依据                                        | 报表标签        |
| ------ | ------------------------- | ------------------------------------------- | ----------- |
| `None` | **不是史低**                  | 与 `price > storeLow` **200/200 完全重合**       | 不进报表        |
| `N`    | **新史低**（本次刷新了历史最低记录）      | `games/history/v2` 复核 **5/5** 为「现价 < 历史旧最低」 | 「新史低」红      |
| `H`    | **平史低**（现价等于已有记录）         | 复核 5 条，**4 条「等于」**（1 条数据稀疏异常）               | 「平史低」橙      |
| `S`    | **仅 Steam 店史低**（别的商店更便宜过） | 复核 3 条全部「等于」；恒满足 `storeLow > historyLow`    | 「店史低」灰 + 标注 |

> ⚠️ **不能**用 `price` 与 `storeLow` 比大小来区分新/平史低。因为 `storeLow` 已含当前折扣，
> 即便刷新了记录，`price` 也等于 `storeLow`（实测 1228 个付费史低候选里
> `price < storeLow` 为 **0** 个）。**判新/平必须看** **`flag`。**

#### ✅ 服务端 filter：一次查询就拿到「本体游戏 + 全部史低」

`/deals/v2` 的 `filter` 参数直接接受 JSON（形如 `filter={"cut":{"min":50,"max":null}}`），
**这是把每轮成本压下来的唯一有效手段**。可用字段（第 24 轮实测，共 148 次请求）：

| 字段                                                                                 | 语义                                        | 实测                                                  |
| ---------------------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| `type`                                                                             | `[1]`=本体 / `[2]`=DLC / `[3]`=包 / `[7]`=软件 | 单页 200/200 全是 `type=game`                           |
| `flag`                                                                             | 史低标记，**层级语义**                             | 见下                                                  |
| `cut` / `price` / `regular`                                                        | `{"min":…,"max":…}` 区间                    | 可用                                                  |
| `steamCount`                                                                       | Steam 评价数区间                               | `{"min":100}` → 20 页 / 3864 条                       |
| `steamPerc`                                                                        | Steam 好评率                                 | ⚠️ 值域见下                                             |
| `added`                                                                            | 「ITAD 在最近 N 小时**发现**的折扣」                  | `added=24` + `type=[1]` + `flag=N` → **1 页 / 69 条** |
| `expiry` / `releaseDays` / `releaseDate` / `shops` / `drm` / `platform` / `mature` | 同类                                        | 未逐个测                                                |

##### ⚠️ `flag` 是**层级**语义，不是等值匹配

实测（国区、`shops=61`、`limit=200`、逐页翻完）：

| 查询                         | 页数   | 条数        | 对照状态库                             |
| -------------------------- | ---- | --------- | --------------------------------- |
| `{"type":[1], "flag":"N"}` | 7 页  | **1,223** | `flag=N` 有 **1,224** 条 ✅          |
| `{"type":[1], "flag":"H"}` | 23 页 | **4,530** | = N(1224) + H(3310) = **4,534** ✅ |
| `{"type":[1], "flag":"S"}` | 27 页 | **5,243** | = 全部史低 **5,246** ✅                |

即 `N ⊂ H ⊂ S`：`flag="S"` 返回**全部史低**（所以它那一栏最多）。

→ **`filter={"type":[1],"flag":"S"}`** **一次查询 = 「本体游戏 + 全部史低」= 27 页 / 5243 条**，
替代无 filter 的 162 页 / 32364 条。且**不影响攒库** —— 状态库本来就只记录史低条目。

**交叉验证**：`{"type":[1]}` 单查得 **48 页 / 9531 条**，与客户端筛出的 **9535 条**吻合
（差 4 条是两次调用之间的数据抖动）→ **服务端** **`type`** **过滤与客户端过滤结果一致，可放心用**。

##### ⚠️ 三个会静默出错的坑

1. **`steamPerc`** **的值域文档写错了。** OpenAPI 写 `minimum: 0, maximum: 100`，
   实测**必须传 0\~1 的小数**：传 `{"min":70}` → **0 条**（不报错，静默返回空）；
   传 `{"min":0.7}` 才正常。
2. **`flag`** **传数组会被静默忽略。** `{"flag":["N","H","S"]}` 的返回结果与**完全不传 filter 一样**，
   不报错、不过滤。只能传单值（要「全部史低」就是 `"S"`）。
3. **`sort`** **只接受网站折扣列表那几个值。** `-cut` / `price` 可用；
   `-timestamp` / `timestamp` / `added` / `-added` / `release` / `-release`
   一律 **400** **`Unknown 'sort' value`** → 「按时间排序」做不到。

以上三条的一次性代价：单跑 `--audit`（无 filter 全量）即可保住
`type_not_game` / `not_historical_low` / `flag_price_mismatch` 这些诊断计数。

#### ✅ 实测规模（国区，2026-09-21 全量复核）

> 早前版本写「> 5000 条」「史低候选 1228 个」，那是**只翻了前 25 页的样本统计**。
> 下面这组是翻到 `hasMore=false` 的全量数字。

- 折扣条目 **32,364 条 / 162 页**（`limit=200`）
- `type` 分布：本体 `game` **9,535** · 非本体 **22,829**（其中 DLC / 包 / 无 type 合计，
  占 70.5%）
- **`type = None`** **是什么？→ 实测抽 15 条，15/15 全是原声带（Soundtrack）**
  （共同特征：标题带 Soundtrack、`tags=[]`、`achievements=False`、多数无封面）
  → 结论：**只保留** **`type == "game"`**，`None`/`dlc`/`package` 一律排除
- `mature` **恒为 False** —— ITAD 默认就不返回成人内容，无需自己过滤
- 价格为 0 的条目极少（5000 条里 4 条）
- **史低（`type=game`** **+ 付费 +** **`flag != None`）= 5,246 个**，
  其中 **`N`（新史低）1,224 ·** **`H`（平史低）3,310 ·** **`S`（店史低）712**
- 距到期分档：24 小时内 **2,065** · 1\~7 天 **1,746** · 8\~14 天 **1,422** · 14 天以上 8
  → 「即将过期（<48h）」口径实测 **2,406 条**，其余视图上线后是千级体量，分页要重新设计

#### ✅ `GET /games/info/v2` 细节

- **返回的是对象（不是数组）**，且**严格一游戏一请求**：
  `?ids=a,b` 报 400，`?id=a&id=b` 只返回最后一个
- 返回 `appid`（Steam AppID）、`reviews[]`、`tags`、`developers`、`publishers`、
  `releaseDate`、`players`、`stats`、`urls.game`
- `reviews[]` 结构：

```json
[
  {"score": 100, "source": "Steam", "count": 10, "url": "https://store.steampowered.com/app/2484180/"},
  {"score": null, "source": "Metacritic User Score", "count": 1, "url": "..."}
]
```

`score` 是 0–100 好评率，`count` 是评价数。**必须只取** **`source == "Steam"`** **那条**，
并**同时卡** **`count`**。

### 2.2 Steam 官方 API（**元数据主源** + 跨区比价）

> ⚠️ **重构（S1/S2）后主源已变**：中文名 / 好评率 / 评价数 / 厂商 / 价格的主源是
> Steam `IStoreBrowseService/GetItems/v1`（批量，见 §2.5）；本节描述的 `appdetails` / `storesearch` /
> `appreviews` 现分别用于**跨区价格**、**降级**与**补充**。`appreviews` 端点 2026-10-22 PT 停用，本项目已不再依赖它。

✅ 实测本地可直连，三个端点全部可用。**全部不消耗 ITAD 配额。**

#### `GET /api/appdetails` —— ⚠️ 批量**只能拿各区价格**（中文名主源已改 `GetItems`，见 §2.5）

```text
GET https://store.steampowered.com/api/appdetails
    ?appids=<appid1>,<appid2>,…      ← 逗号分隔
    &cc=ua|in|cn                     ← Steam 区码，小写
    &l=schinese                      ← 中文名的来源（**只在单 appid 时有效**）
    &filters=price_overview
```

**实测出来的 filters × appid 个数规则（第 27\~28 轮，共 30 次请求）**：

| 场景          | `filters`                                                            | 结果                                                 |
| ----------- | -------------------------------------------------------------------- | -------------------------------------------------- |
| **单** appid | 任意值 / 不带                                                             | 200，`data` 里有 `name` + `price_overview`            |
| **多** appid | **只有** **`price_overview`**                                          | 200，每个 appid 都有 `price_overview`，**没有** **`name`** |
| **多** appid | 其他任何值（`basic` / `release_date` / `developers` / `platforms` / …）/ 不带 | **400**                                            |

- ❌ **修正**：早前本文写的「`appdetails` 支持批量，**能同时给中文名与各区价格**」、
  「`filters=basic,price_overview` 批量有效」**都是错的** —— 那次验证用的是**单 appid**。
  现在实测：**多 appid +** **`basic`** **一律 400**；`price_overview` 能批量但**不返回** **`name`**。
- ✅ **批量有效（仅价格）**：`appids=<20 个>&cc=ua&filters=price_overview` → 200，20 个 key 全部返回。
  实测一次 20 个正常；文档说的 50 未复核，`steam_batch_size` 默认取 **20**。
- ✅ **中文名**：单 appid + `filters=basic,price_overview` + `l=schinese` → `data.name`
  就是官方中文名（`Cyberpunk 2077` → `赛博朋克 2077`）。
  **注意**：Steam 上没有中文标题的游戏会返回英文名（例如 `Watch_Dogs® 2`），
  这**不是失败**，按 §11「没有中文名就回落英文名」处理。
- ⚠️ `filters=basic` 会带上 `detailed_description`，单 appid 就有约 21 KB（不带 filters 更大）。
  所以中文名要逐游戏取 —— **必须缓存**，见 §2.5。
- 永久免费游戏（CS2 / Dota2 / TF2）返回 `data: []`，属正常（客户端已跳过并计数）

#### ⚠️ appid 重定向：带 `basic` 时响应的 key 不是 appid（2026-09-25，共 41 次请求）

单 appid 且 `filters` 含 `basic` 时，**响应的 key 是「店铺页 id」**，与请求的 appid 不同：

| 请求 | 返回 key |
| --- | --- |
| 单 + 不带 `filters` ／ `basic` ／ `basic,price_overview` | **店铺页 id** ★（412020 → 1952352、1091500 → 2441600、597820 → 1549560） |
| 单 + `price_overview` | 请求的 appid（412020） |
| 多 + `price_overview` | 与请求**等值且同序** |

- 该 key **不是 appid**：直接请求 1952352 会 `success: false`、没有 `data`。
- 与区域、语言**都无关**：`cc` 换 us / ua、`l` 换 english，返回 key 都不变（只有 `name` 变）。
  即中文名只取决于 `l=schinese` —— 不存在「全球 id 没中文名、国区 id 才有」这回事。
- `basic` 响应里的 `data.steam_appid` 等于请求的 appid（`price_overview` 下不带该字段）
  → 是同一个游戏，不是「另一个版本」。
- ⚠️ **`name` 只有 `basic` 能给，所以重定向不可回避**。客户端 :meth:`SteamClient.info`
  取「响应里的唯一值」而不是按 key 查 —— 曾经的 `data.get(appid)` 写法会静默拿不到名字，
  导致大量中文名丢失（2026-09-25 修复）。
- ✅ **批量价格路径不受影响**（曾经担心的错配已证伪）：`price_overview` 批量返回的 key
  与请求等值同序，`src/enrich.py` 按请求 appid 查表是安全的。
- 影响面：`title_zh=None` 的条目里约 **45%** 是重定向导致的丢失，但抽 20 条实测只有
  **30%** 能补出中文名 —— 其余 Steam 上本就只有英文名（属 §11 的正常回落）。
  详见本地 `.scratch/appid-redirect/fix-round1.md`（不入库）。

#### ⚠️ 探针也不能突发打 Steam（第 27\~28 轮的教训）

无间隔地连打约 40 次 `store.steampowered.com` 之后，
**该 host 的全部端点开始静默超时**（连对照组 `appdetails` 都连不上，
表现为 `ConnectTimeout` / `SSLError: CERTIFICATE_VERIFY_FAILED`），
约十几分钟后自行恢复。这正是 §2.2「突发本身就是触发条件」的实证。

→ **探针脚本必须走同一套节流**（最小间隔 2 秒）。
`tools/probe_steam_*.py` 已加 2.5 秒硬间隔；`tools/check_steam.py` 用的是项目客户端 + `RateLimiter`。

#### ⚠️ 本机对 `store.steampowered.com` 有 TLS 拦截：必须用系统证书库

本机装了 **SteamTools（Watt Toolkit）**，它会对 `store.steampowered.com` 做 TLS 中间人加速。
实测对端证书的签发者是 `SteamTools Certificate / BeyondDimension`，
而 `api.isthereanydeal.com` / `open.er-api.com` 都是正常的公开 CA（Google Trust Services）。

后果：`requests` 默认只信任它自带的 `certifi` 证书列表，里面**没有** SteamTools 的根证书
→ **`SSLError: CERTIFICATE_VERIFY_FAILED`**。而同一个 URL 用 `urllib` 能通，
因为 `ssl.create_default_context()` 会加载 **Windows 证书库**（SteamTools 的根证书装在那里）。

→ 本方案的做法（`src/httpclient.py`）：**并不关掉校验**，而是把**可信来源**换成
系统证书库 —— 先把 Windows 的 `ROOT`+`CA` 证书导成一个 PEM
（`ssl.enum_certificates`，注意 encoding 字段是 **`x509_asn`** 不是 `x509`，
写错一个字符就一个证书都导不出来、然后静默退回 certifi），缓存到 `data/ca_bundle.pem`，
再赋给 `session.verify`。这就是浏览器和 curl 用的那套信任来源。

优先顺序：`REQUESTS_CA_BUNDLE` / `CURL_CA_BUNDLE` / `SSL_CERT_FILE` 环境变量
→ 系统证书库 → 退回 requests 默认（certifi）。
**GitHub Actions 的 Linux runner 上没有这个拦截**，会自然走 certifi，不受影响。

#### `GET /api/storesearch` —— 英文名 → appid + 中文名

```
GET https://store.steampowered.com/api/storesearch/?term=<英文名>&cc=cn&l=schinese
```

返回 `items[]`，每项有 `id`(appid) / `name`(本地化名) / `price`。
实测 `term=赛博朋克` → `赛博朋克 2077`；`term=NBA 2K26` → appid 3472040。
⚠️ 结果是**排名列表**且会混入 DLC / 通行证 / Demo，必须做名称精确匹配后才采用。

#### `GET /appreviews/<appid>` —— Steam 官方好评率

```
GET https://store.steampowered.com/appreviews/<appid>?json=1&num_per_page=0&language=all&purchase_type=all
```

返回 `query_summary`：`total_positive` / `total_negative` / `total_reviews` / `review_score_desc`。
✅ 与 ITAD 交叉验证一致：Watch Dogs 2 = 84073/102417 = **82.1%**，ITAD 报 **82**。

#### ⚠️ Steam 限流（按社区经验设定，**不做实测**）

**第一件事：先分清三个完全不同的表面**，混为一谈是各种错误数字的来源：

| 表面                                             | 限流机制                                   | 本方案     |
| ---------------------------------------------- | -------------------------------------- | ------- |
| `store.steampowered.com/api/*`、`/appreviews/*` | **未公布**，只有经验观测；**per-IP**              | ✅ 我们用这个 |
| `api.steampowered.com`（带 key）                  | 官方条款 **10 万次/天/密钥**；另有未公布的 per-IP 突发上限 | 不使用     |
| Steam 社区市场                                     | 独立节流机制                                 | 不使用     |

**Valve 从未公布 Storefront 的任何数字阈值**，下面所有数字都是社区经验观测。

##### 两个约束，缺一不可

1. **平均速率**：多数来源口径 **约 200 次 / 5 分钟 / IP**（= 40 次/分钟），
   也就是社区常说的「**每 1.5 秒 1 次**」。`apis.io` 的限流档案另给
   「约 1 次/秒」，更宽松——**取保守的那个**。
2. **并发**：这一条容易被忽略但很关键 —— **并发本身就是触发条件**。
   `apis.io` 明确写「**Sustained high concurrency from a single IP returns 429**」。
   所以只做速率控制不够，**必须同时限制并发数**。

**本方案：store.steampowered.com 全站按同一个预算合并计数 + 串行 + 最小间隔 2 秒。**

> 为什么是「合并计数」：`appdetails` 与 `appreviews` 在**同一个 host** 下，
> 没有证据表明它们各自独立配额，**保守假设它们共享 per-IP 预算**。
> 因此不设两套窗口，只设一套总窗口（见 §3.3）。
>
> 为什么不靠滑动窗口就够：窗口只约束「平均」，不约束「瞬时并发」。
> ⚠️ 早前本文写过"评测接口比 `appdetails` 严约 16 倍"，是**算错了**——
> 那个说法也不成立，社区原文的定性（"Review API is more restrictive"）
> 与它自己给出的数字相矛盾。

##### ⚠️ 429 不止一个原因：五种响应必须分开处理

| 响应                             | 含义                | 处理                                        |
| ------------------------------ | ----------------- | ----------------------------------------- |
| **429**                        | 速率/并发超限           | 尊重 `Retry-After`；没有则从 **10 秒**起退避，逐步加到分钟级 |
| **403**                        | **滥用封禁，比 429 严重** | 社区做法是**等 5 分钟**；连续出现则中止本轮并告警              |
| **200 但 body 是字面量** **`null`** | **软限流**（不报错，悄悄限你） | **必须当限流处理**，不能当成"没数据"                     |
| **200 且** **`success: false`** | **不是限流**          | appid 不存在 / 该区不售，记 run\_log 后跳过           |
| **503**                        | **服务端故障**，与限流无关   | 重试，不计入限流统计                                |

**绝不可以用轮换 IP 的方式规避限流**（社区明确不建议；长期滥用会导致密钥/IP 封禁）。

##### 另外两条影响实现的

- **多 appid 必须带** **`filters`** **才能批量**（不带会失败）。本题实测
  `filters=price_overview` 传 2 个 appid 成功；社区实测一次可传 **50 个**
- Valve 建议仍可用官方 Web API 的场景就走官方（配额更宽松、有支持），
  但我们需要的价格/评测数据只在 Storefront 上

##### 由此得出的调度结论

按上面的保守设定（Steam store 全站 **150 次 / 5 分钟 = 30 次/分钟**，串行且间隔 ≥2 秒；
ITAD **800 次 / 5 分钟 = 160 次/分钟**）：

| 通道                 | 单请求承载          | 有效速率                      | 1228 个游戏耗时 |
| ------------------ | -------------- | ------------------------- | ---------- |
| Steam `appdetails` | **50 个游戏**（批量） | 30 请求/分钟 → **1500 游戏/分钟** | **约 1 分钟** |
| Steam `appreviews` | 1 个游戏          | 30 / 分钟                   | 约 41 分钟    |
| ITAD `info/v2`     | 1 个游戏          | 160 / 分钟                  | **约 8 分钟** |

- **批量能力**上 Steam `appdetails` 断层第一 → **各区价格走它**（**注意：批量拿不到** **`name`**，中文名要逐游戏取，见 §2.2）
- **单游戏**场景下 ITAD 比 Steam 快约 **5 倍**，且 `info/v2` 顺带给出 appid
  → ⚠️ **已过时**：重构（S1/S2）后**好评率主源改为 Steam `GetItems`**（批量一次带中文名 + 好评率 +
  评价数 + 厂商），ITAD `info/v2` 仅作**降级**。此行保留作沿革。
- ⚠️ 更正：早前本文说 "`appreviews` 占用另一条独立配额，可与 ITAD 并行分流" ——
  既然保守假设 Steam store **全站共享 per-IP 预算**，就**不能**把 `appreviews`
  当成独立通道来并行加量。它只作补充/兜底。

#### ✅ ITAD 不能用于跨区比价

实测同一个游戏（appid 2000040 Space Menace）各地区报价：

| 来源                                     | 币种                    | 原价                           |
| -------------------------------------- | --------------------- | ---------------------------- |
| Steam 官方 `appdetails?cc=ua`            | **UAH**               | **170₴**（≈4.10 USD）          |
| ITAD `country=UA`                      | USD                   | **6.99** ← 和 US 一模一样         |
| ITAD `country=US`                      | USD                   | 6.99                         |
| ITAD `country=GB` / `DE` / `BR` / `TR` | GBP / EUR / BRL / TRY | 6.29 / 7.19 / 26.75 / 228.87 |
| ITAD `country=CN` / `IN`               | CNY / INR             | 29 / 359                     |

**ITAD 不识别** **`UA`，静默返回了默认地区（US）的价格**——不报错，只是悄悄给你美国的价。
`GB`/`DE`/`BR`/`TR`/`CN`/`IN` 都正常。这是个阴险的坑。

→ **跨区比价一律走 Steam 官方接口**，且**以后每新增一个地区都要先跟 Steam 校准一次**。

```
GET https://store.steampowered.com/api/appdetails
    ?appids=<appid1>,<appid2>,…     ← 支持逗号批量
    &cc=ua|in|cn                    ← Steam 官方代码，小写
    &filters=price_overview
```

优点：**原生币种**（UAH / INR / CNY，权威）、**支持批量 appid**、**不消耗 ITAD 配额**。
注意：永久免费游戏（CS2 / Dota2 / TF2）返回 `data: []`，属正常。
（批量返回**非空**数据这一条还没在付费游戏上直接验证，实现时第一件事就补验。）

### 2.3 汇率源

UA→UAH、IN→INR、CN→CNY，三币种不统一，算「差价百分比」必须换汇。
**每日取一次并缓存**，**页面上必须标注汇率数值与取数日期**（§7.4）。

实测两个候选（`data/probe/summary26_steam.txt`）：

| 源                                   | 有 UAH？       | 返回的取数日期                      | 结论              |
| ----------------------------------- | ------------ | ---------------------------- | --------------- |
| **`open.er-api.com/v6/latest/CNY`** | ✅ 有          | `time_last_update_utc`（可直接用） | **采用**          |
| `frankfurter.app/latest?from=CNY`   | ❌ **没有 UAH** | `date`                       | 不能用（基于 ECB 币种表） |

实测返回（2026-09-21）：`UAH=6.67391`、`INR=14.303287`、`USD=0.149149`。
`rates[X]` 的含义是 **1 个基准币能换多少 X**，所以 `X → CNY` 是**除以**它：

```
UA 45₴ = 4500 戈比 → 4500 / 6.67391 ≈ 674 分 = ¥6.74
IN ₹149 = 14900 paise → 14900 / 14.303287 ≈ 1042 分 = ¥10.42
```

方向写反不会报错、只会给出荒唐的比价结论，所以 `tests/test_fx.py` 专门钉了这一点。
汇率源挂了**不让整轮失败**：沿用缓存里的旧值并在日志里告警。

### 2.4 已排除的方案

| 方案                                | 排除原因                                           |
| --------------------------------- | ---------------------------------------------- |
| Valve 官方 Web API 判史低              | **完全不提供历史价格**                                  |
| SteamDB 抓取                        | Cloudflare 反爬 + 违反 ToS                         |
| SteamDB 第三方代理（Anysite）            | \$49/月起，个人工具不划算                                |

| `ISteamApps/GetAppList` 批量拿 appid | 要按**游戏名模糊匹配**，版本后缀/本地化差异会错配；而且**不省请求**（见 §3.3） |
| 好评率改从 Steam 取                     | Steam 评测接口同样只有逐游戏调用，绕一圈请求数不减反增                 |

### 2.5 ✅ 数据源职责划分（长期收敛方向）

**后期 ITAD 只负责「判断哪些是史低」，其余展示数据全部走 Steam。**

| 职责                     | 首选                                  | 备选                            | 说明                                                 |
| ---------------------- | ----------------------------------- | ----------------------------- | -------------------------------------------------- |
| 判史低（`flag`）/ 折扣起止 / 封面 | ITAD `deals/v2`                     | —                             | ITAD 唯一不可替代的能力                                     |
| 上一次史低时间                | ITAD `storelow/v2`（**批量**）          | —                             | 只有 ITAD 有这个数据，见 §3.6                               |
| appid                  | ITAD `info/v2`                      | `itad.link` 短链（**零 ITAD 配额**） | 逐游戏，无法批量                                           |
| 好评率                    | **ITAD** **`info/v2`**              | Steam `appreviews`            | ITAD 160/分钟 vs Steam store 30/分钟，且顺带给 appid，见 §2.2 |
| 各区价格                   | **Steam** **`appdetails`（批量）**      | —                             | 每区 1 次请求覆盖整个列表                                     |
| 中文名                    | **Steam** **`appdetails`（单 appid）** | `storesearch`                 | ⚠️ **无法批量** → 必须永久缓存（§2.2 / §2.5）                  |
| 汇率                     | 第三方汇率 API                           | —                             | 每日一次并缓存                                            |

长期稳态下 ITAD 每天只承担：\*\*`deals/v2` 翻页（约 30 次）

- `storelow/v2`（约 7 次）+ 当日新增的 `info/v2`（几十\~几百次）\*\*。

缓存更新策略：

- `appid`：**永久有效**，不更新
- `reviews`：TTL 7 天。更新时**优先走 ITAD** **`info/v2`**（顺带校验 appid）；
  仅当 ITAD 不可用时才回落到 Steam `appreviews`
- `各区价格`：**S7 换模型（2026-10-05）——原价永久缓存 + 现价真查**。
  `compare_cache` 键改 `<appid>|<cc>`，存区域**原价**（`price_overview.initial`），
  不随折扣期失效、不参与留存清理；现价（`final`）每轮对进列表条目**真查**
  （当日新增 + 即将过期合并去重，20 个/批），真查响应里的原价与缓存比对
  —— 不一致即 Valve 区域重定价，回写自愈并记日志（「真查即校准」）。
  旧方案 B（键 `<appid>|<expiry>` 存折扣现价）废弃：final 与 initial 不是
  同一个量，旧格式键在加载时自动丢弃（清空重建，新缓存由真查零成本自建）。
  只存原币种原价，CNY 换算与差价百分比按当天汇率渲染时现算；
  **整区真查失败时该区该轮缺行**（不回落，下轮自愈）
- `中文名`：⚠️ **要缓存，而且永久有效**。原因见 §2.2：`name` 只在**单 appid** 的
  `appdetails` 里返回，**没法批量**，一个游戏一次请求。所以存进 `game_meta.title_zh`，
  只在第一次遇到时取；实测一个游戏的中文标题不会变。
  （早前本文写的「中文名每次实时拉、不进缓存」，前提是「批量接口成本可忽略」——
  那个前提**不成立**，已更正。）
  与 `reviews` 是**两条独立缓存**：`set_title_zh()` 不碰 `fetched_at`，
  否则会把好评率的 TTL 一起刷掉。

## 3. 抓取流程与请求预算

### 3.1 流水线

```
① 抓折扣列表        ② 筛选链             ③ 判史低        ④ 判当日新增
   GET /deals/v2  →  type==game      →   flag != None  →   timestamp=今天
   （国区，翻页）     排除免费             （N/H/S）        （主口径，
                      折扣阈值                              本地状态仅兜底）
                      折扣阈值
                                                              ↓
                    ⑦ 报表输出        ←  ⑥ 跨区比价      ←  ⑤ 取详情（仅当日新增）
                       index.html       Steam appdetails    info/v2 → appid+好评率
                       data.js          appids 批量         + 好评过滤
                       latest.json      cc=ua/in/cn
```

### 3.2 筛选链与各步规模（实测）

抓取口径（`sweep_mode`）决定「从全量开始筛」还是「让服务端先筛掉」：

| 口径                 | `/deals/v2` 请求 | 拿到的条目          | 说明                                      |
| ------------------ | -------------- | -------------- | --------------------------------------- |
| `low_only`（**默认**） | **27 页**       | 5,243（本体 + 史低） | `filter={"type":[1],"flag":"S"}`，见 §2.1 |
| `full`（`--audit`）  | **162 页**      | 32,364（全部折扣）   | 无 filter，用于体检与交叉校验                      |

`low_only` 口径下的筛选链（**实测，国区 2026-09-21**）：

| 步骤            | 条件                        | 剩余规模                         |
| ------------- | ------------------------- | ---------------------------- |
| 抓取（服务端已过滤）    | `type=[1]` + `flag=S`     | **5,243**                    |
| 排除免费          | `price > 0`               | \~5,240                      |
| 判史低（服务端给的是超集） | `flag != None`            | **5,243**（与实际 5,246 之差为数据抖动） |
| 当日新增          | `timestamp` = 今天 或 本地首次见到 | **实测 105\~106 条**            |
| 取详情           | 当日新增里缓存未命中的               | 首轮 105 → 之后每天几十\~几百          |
| 好评过滤分档        | 见 §3.5                    | **进列表约 20 条**（106 个新增里）      |

`full` 口径下（体检用）能额外得到：
本体 9,535 · 非本体 22,829 · 非史低 4,286 · `flag` 分布 N=1,224 / H=3,310 / S=712。

> ⚠️ `low_only` 口径下 `type_not_game` / `not_historical_low` / `flag_price_mismatch`
> 三个计数**必然为 0** —— 那不是「今天没有异常」，而是这两个口径看不到，
> 必须在 `run_log` 里连同 `sweep` 一起记录，否则会被误读。
>
> 每一步「砍掉多少条」都要写进 `run_log`，便于按真实数字调阈值。

### 3.3 请求预算

**关键约束：`info/v2`** **一游戏一请求、没有批量端点。** ✅ 已实测确认：
`POST /games/info/v2` 返回 **405**；`POST /games/overview/v2` 虽然接受数组能批量，
但只返回价格与最低价，**不含** **`appid`** **和** **`reviews`**，替代不了。
（`storelow/v2`、`historylow/v1`、`prices/v3` 这些能批量 200 个 id，但都不含 appid/好评率。）

所以「appid + 好评率」只能逐游戏取，1 次/游戏。但**可以选在哪一侧付这个成本**：

| 路径        | 每游戏请求                                   | 计入谁的配额 | 备注                          |
| --------- | --------------------------------------- | ------ | --------------------------- |
| **A（推荐）** | 1 次 ITAD `info/v2`                      | ITAD   | 一次同时给 appid + 好评率，最省        |
| B（分流备用）   | 2 次 Steam（`storesearch` + `appreviews`） | Steam  | 总请求翻倍，但 ITAD 用量可压到 \~30 次/轮 |

路径 B 的用法：大促等极端情况下一轮要抓几千个详情时，用 Steam 分流避免撞 ITAD 限流。

#### ⚠️ 大促爆发：一天几千条史低怎么办

实测过：单次大促首日，「当日新增」可能等于全部史低候选（**几千条**），
而每游戏要 1 次 `info/v2`。**结论：这仍然可行，限流不是障碍，关键是节流方式。**

- ITAD 的 **1000 请求 / 5 分钟是「速率限制」，不是每日配额** ——
  每天总请求量**没有上限**，只要节流得当，多抓几千条完全可行
- 3000 个详情 ≈ 3 个限流窗口；按每次约 0.4s 的实际耗时，**约 20 分钟抓完**
- 一天两次运行（3:00 + 8:00），时间上完全宽裕

必须做的三件事：

1. **限流要做三件事，只做滑动窗口不够。** 记录每次请求的时间戳，按通道分别约束：
   | 约束            | ITAD           | Steam store（`store.steampowered.com` 全站合并计数） |
   | ------------- | -------------- | -------------------------------------------- |
   | 上限（官方 / 社区观测） | 1000 / 5 分钟    | \~200 / 5 分钟（即每 1.5 秒 1 次）                   |
   | 本方案 · 窗口      | **800 / 5 分钟** | **150 / 5 分钟**                               |
   | 本方案 · 最小间隔    | 0.3 秒          | **2 秒**                                      |
   | 本方案 · **并发**  | **串行（1）**      | **串行（1）**                                    |
   | 余量            | 20%            | 25%                                          |
   - ⚠️ **必须同时限制并发数**：限流不只看总量——**持续高并发本身就会触发 429**。
     把并发压到 1（串行）是最省心的做法，对本项目的量级完全够用
   - Steam 侧不设两套窗口：`appdetails` 与 `appreviews` 同 host，
     **保守假设共享 per-IP 预算**，合并计数
   - 固定 sleep 只是碰运气，大促时极易撞 429
   - 遇到 429/403 就**自动降速**并把事件写进 run\_log——这是唯一需要的「被动调参」依据，
     **不需要主动去探顶**
2. **报表与详情解耦：报表永远不等详情。** 先用缓存渲染出页面，
   缺详情的卡片标「详情待补」，详情在同一次运行里边抓边补。**页面立刻可看。**

   落地方式：把「合并缓存 → 多版本去重 → 分档 → 渲染」抽成一个可重复调用的
   `render_pass()`，在 `run_daily` 里调两次 ——
   **第一次在取详情之前**（缺的标「详情待补」），**第二次在取完之后覆盖同一份文件**。
   两次用同一个 `now`，保证页面上的生成时间与 `?v=` 不跳动。
   （2026-10-09 起该函数与 `merge_details` / `build_stats` / `count_backlog` 一起
   住在 `src/pipeline.py`；`run.py` 只**编排**并转发导出这几个名字，
   这样 `tools/render_report.py` 这类零网络的渲染工具不必 import 入口 module。）

   同一段代码里还有一条必须绑在一起的约束：**写完** **`seen_deal`** **立刻** **`save()`**。
   否则一旦详情全部失败（`fetched` 恒为 0，中间那次落盘永远不触发），
   这一轮 5000 多条攒库会被一起丢掉。
3. **断点续传 + 优先级。** 详情按 uuid 逐条落盘，优先抓「当日新增」，
   抓不完的下次运行接着抓（缓存命中自动跳过）。

极端情况（一天上万条）再加一层：**启用 Steam 分流（路径 B）**，把 ITAD 用量压到最低。

#### ✅ appid 获取路径 与 ITAD↔Steam 映射能力

> 更正：早前判定「反查端点已损坏」是**误判**，错在传参格式。正确格式见下。

**映射能力双向都存在**（第 16–23 轮实测）：

| 方向           | 端点                             | 批量               | 结果                                                   |
| ------------ | ------------------------------ | ---------------- | ---------------------------------------------------- |
| appid → uuid | `POST /lookup/id/shop/61/v1`   | ✅ **单次 10000 条** | body 必须是 `["app/<appid>"]`；**前缀** **`app/`** **不可省** |
| appid → uuid | `GET /games/lookup/v1?appid=`  | ❌ 单条             | 与上者 **15/15 一致**                                     |
| uuid → appid | `GET /games/info/v2?id=<uuid>` | ❌ 单条             | type=game **15/15 都有** **`appid`**                   |

- 错误传参 `["447040"]` / `["steam:447040"]` / `[447040]` 一律返回 `null`（早前就是这么测的）
- 官方**无可下载的全量映射表/dump**；`/v01/game/plain/list/` 与 `/games/plain/v2` 都是 **404**

**⚠️ 映射不是双射。** 同一 appid 在 ITAD 可能有**多个条目**——Steam 页面改版时 ITAD 会另建
新条目，而**旧条目仍留在 deals 里流通**。实测 15 条里 4 条如此：

| appid   | deals 里的条目                                   | 批量端点返回的"规范条目"                     |
| ------- | -------------------------------------------- | --------------------------------- |
| 266230  | Last Dream - **Deluxe Edition** (Game + OST) | Last Dream                        |
| 1019590 | Lovely Planet 2                              | Lovely Planet 2: **April Skies**  |
| 944220  | Gachi clicker                                | Gachi **Heroes**（type=None）       |
| 770070  | Swords and Sandals 5 Redux                   | …: **Maximus Edition**（type=None） |

所以：**appid → uuid 是一对多**（端点只返回"规范主条目"，与 deals 的 uuid 一致率 11/15）；
**uuid → appid 是多对一、可靠**。

**规模**：`GET /service/shops/v1` 显示 Steam(61) `games = 310,642`、`deals = 35,785`。
枚举 appid 区间实测命中率 **7.24%**，全量 350 万 appid ≈ **350 请求**——
但如前所述，自建表方向不对，**结论是不做**。

**→ uuid → appid 仍只有两条路：**

| 路径                             | 请求成本   | 计入配额          | 说明                                             |
| ------------------------------ | ------ | ------------- | ---------------------------------------------- |
| `GET /games/info/v2?id=<uuid>` | 1 次/游戏 | ITAD          | **顺带返回好评率**，首选                                 |
| 跟随 `deal.url`（`itad.link` 短链）  | 1 次/游戏 | **零 ITAD 配额** | 落地即 `store.steampowered.com/app/<appid>/`，正则解析 |

批量端点只在「**已知一批 appid → 批量换 uuid**」这个方向有价值（如将来做愿望单同步）。

**「越跑越全」是天然成立的**：某个游戏只要**下一次重新打折**，它就会重新进入
「当日新增」，那一刻自然抓到详情并写进缓存。所以不存在「永远补不上」的情况。

**真正的解法：分层 + 缓存 + 增量。**

#### ✅ 本方案：当日新增全抓 + 目录按预算增量补

| 阶段                     | 请求构成                                                          | 量级（实测 / 估算）                  |
| ---------------------- | ------------------------------------------------------------- | ---------------------------- |
| 首次 `--baseline`        | **只翻页抓列表写入状态**，不取详情                                           | **20\~27** 次（`full` 口径是 162） |
| 日常每次运行                 | 翻页列表 + **详情目标全部抓**（S2 起派生式欠账**不设预算**：当日新增 ∪ 折扣活跃超 TTL ∪ unlisted 重判） | **27 + 目标数（通常几十\~几百）**       |
| `--audit`（按需）          | 无 filter 全量翻页，保住 `type`/`flag` 全分布与 §4.1 交叉校验                 | **162** 次                    |
| 中文名（第 7 步）             | 逐游戏单请求、**永久缓存**，只有从没见过的才发                                     | 首次 = 进列表条数；之后 ≈ 当天新增进列表数     |
| 跨区比价（第 7 步）            | Steam `appdetails` 按 appid **批量**（20 个/批），每区 1 组，**不占 ITAD 配额**；S7 起现价每轮真查 + 原价回写校准 | 进列表 appid ÷ 20 × 区数（UA + IN） |

每天 2 次运行（主跑 + 补跑），全天合计约 **700\~1400** 次 ITAD 请求 ——
**仍远低于 1000 次/5 分钟**（那是**速率**窗口，不是每日上限）。

> 第 24 轮之前每轮固定 **267 次**（162 + 105 详情）；改为 `low_only` 口径后约 **132 次**。

##### 详情抓取范围（历史：`detail_scope` 两段式 → S2 派生式取代）

用户要求「**详情只跑符合要求的史低游戏目录，不要每轮全跑一遍**」。旧方案是
「当日新增全抓 + 目录按 `detail_daily_budget` 增量补」；**S2 重构起被派生式欠账取代**：

    目标 = 当日新增 ∪ 折扣活跃且数据年龄超 TTL ∪ unlisted 重判（§3.2，不设预算）

命中缓存的直接跳过；页脚里显示**还差多少条**，进度可见。预算与 `detail_scope` /
`detail_daily_budget` 键一并退场。

> ⚠️ **试过一个更省钱的做法，被否掉了**：用服务端 `filter={"steamCount":{"min":100}}`
> 先筛掉「评价数 <100 的冷门」（实测史低 5242 → 2111，页数 27 → 11）。
> **不能这么做**：ITAD 对相当一部分游戏**根本没有 Steam 评测数据**
> （实测当日新增里 39/107 条拿不到好评率），拿它当门槛会
> **静默丢掉 Steam 上其实评价很多的游戏** —— 正是 §3.5 要避免的事。
> 宁可多花请求，也要让客户端拿到全量后自己判档。

> 注意：`--baseline` **不预热详情缓存**。所以「早于上线就已处于史低」的那批游戏
> 一开始没有好评率（显示「详情待补」），靠**每轮 300 条的增量补齐**慢慢填
> （实测当日在补 3116 条 → 约 5 天填完）。

#### 缓存策略

- `appid`：**永久有效**（Steam AppID 不会变）
- `reviews`：**折扣感知四档 TTL**（S6，2026-10-05）：新游（发行 ≤30 天）1 天 /
  到期窗口（expiry −48h 起）1 天 / 折扣期普通条目 3 天 / **非折扣期不刷新**；
  旧的全局 `reviews_ttl_days`（7 天）与 `reviews_empty_ttl_days`（3 天）已废弃删除
- `title_zh`（中文名）：**永久有效**，与 `reviews` 是两条独立缓存（§2.5）
- 缓存命中就不发请求 —— 这是把请求量压下来的关键

#### 一个纠正

「按 appid 去重」**不能**节省 `info/v2` 请求——因为必须先调 `info/v2` 才知道 appid。
它的价值在于：报表不重复展示同一游戏的不同版本，以及**减少 Steam 跨区批量请求**
（每个 appid 只查一次，而不是三个版本各查一次）。

### 3.4 ✅ 好评率阈值：70% + 评价数 ≥100

实测 12 个史低候选：

- 评价数：`[104, 134, 472, 628, 628, 829, 1006, 3274, 30589, 95242, 95242, 95242]`
  → **最小值就是 104**，所以 **100 一条都不误伤**；200 会开始误杀真实的中小体量游戏
  （OVERPASS 104 条、The Dragoness 134 条）
- 好评率：`[51, 60, 60, 61, 67, 71, 77, 77, 82, 82, 82, 82]`
  → **≥70% 通过 7/12**（砍掉约 42%），能有效服务「大促别列几千个」的目标

**结论：好评率 ≥70% 且评价数 ≥100**，两项都可配。

> 诚实说明：这 12 个样本取自高折扣榜，偏热门，**全集的真实裁掉比例会更高**。
> 所以 run\_log 记录每个过滤条件砍掉多少条，用真实数字再调。

### 3.5 ✅ 好评过滤改成分档，而不是硬砍（避免误杀"差评热门游戏"）

实测三个会被 70% 阈值**静默丢掉**的知名游戏：

| 游戏       | 好评率       | 评价数         | Steam 评级 |
| -------- | --------- | ----------- | -------- |
| NBA 2K26 | **64.2%** | 33,378      | Mixed    |
| NBA 2K25 | **59.0%** | 42,942      | Mixed    |
| 使命召唤®    | **58.5%** | **782,040** | Mixed    |

《使命召唤》有 **78 万条**评价——Steam 上评价数最高的游戏之一——却因为 58.5% 好评率被丢掉。
**结论：「热门」的信号是评价数的绝对值，不是好评率。**

分档规则：

| 档位             | 条件                         | 处理              |
| -------------- | -------------------------- | --------------- |
| **好评达标**       | 好评率 ≥70% **且** 评价数 ≥100    | 进主列表            |
| **高热度 · 口碑不一** | **评价数 ≥ 10,000**（不看好评率）    | 单独分组，**置于页面最上方**，默认收起 |
| 冷门 / 无数据       | 评价数 <100                   | 不展示（样本太小，无参考价值） |
| 未达标            | 好评率 <70% 且 评价数 100\~10,000 | 不展示；提供开关可显示     |

> ⚠️ **标签用中性描述，不要用「优质」这类评价性词**：70% 好评率在 Steam 自己的刻度上
> 只是「多半好评」，叫「优质」会让人误判。**入组条件必须写在分组标题旁边**
> （由 `report.group_specs(cfg)` 从配置生成，改阈值文案自动跟着变）。
> **2026-09-24 批 F：页面上那个「筛选条件」折叠卡已删除**（曾经历「列表上方裸 details」→
> 「卡片化留原位」→「顶部一行右侧等高并排」三版），全部判定口径搬到
> `README.md` 的「筛选条件」一节 —— 它是文档，不该占手机屏幕高度；
> `report.py` 随之删掉 `conditions()` / `conditions_digest()` 与对应 payload 字段。

**10,000 这条线的依据**：三个知名作品是 33,378 / 42,942 / 782,040，全部远高于它；
而 12 个史低样本的评价数中位数只有 **917**。所以 10,000 能把「知名作品」和「长尾小游戏」干净分开。

可选的绝对下限 `absolute_min_positive_ratio`（如 40%）：低于此值即便评价数再高也不展示。
**默认不加** —— 卡片本来就默认折叠，放出来让用户自己判断，更符合「感兴趣的自然会点开」。

### 3.6 ✅ 上一次史低时间（批量补，请求量几乎不增加）

`POST /games/storelow/v2`（body 为 uuid 数组，带 `country` + `shops`）返回每个游戏的
商店历史最低价，**并且带** **`lows[].timestamp`** **= 该最低价被记录的时间**。
实测 Deadshot 返回 `4.2 CNY @ 2025-09-18`。

- 它是**批量接口**（文档标注 200 个 id/次）→ 1228 个史低游戏只需**约 7 次请求**，
  完全满足「请求数量不明显增加」的前提
- 解读方式（结合 `flag`）：

| flag      | `lowest.timestamp` 的含义        |
| --------- | ----------------------------- |
| `N`（新史低）  | 时间戳 ≈ 本次折扣开始时间 → **正是这次破的记录** |
| `H`（平史低）  | 时间戳更早 → 就是**上一次达到史低的时间**      |
| `S`（仅店史低） | 同上，但另有商店更便宜过                  |

**✅ 已实现（2026-09-23）**：`run.fetch_last_low_times` + `ItadClient.fetch_storelow`
（响应结构实测见其 docstring）。落地口径：

- 对**当日新增 + 即将过期候选**取（2026-09-27 批 H 扩展：即将过期条目大多从未当过
  当日新增，meta 里没有该字段，报表「距上次史低」整行缺失），每轮**整批重取**
  不做缓存跳过 —— 否则游戏再次新低时会拿过期时间；200 个/批，日常约 1~10 次请求/天
- 存 `low_time_cache`（2026-09-27 批 H 起，**折扣期暂存**：键 `<game_id>|<expiry>`，
  同一游戏多版本折扣各存一份；随 `cleanup_expired` 与 `seen_deal` 同保留期清理）。
  旧 `game_meta.last_low_at` 存量字段留存不迁移，读不再走它，等重取自愈。
  2026-10-09 起查找带回退（精确键 miss → 该游戏折扣期最新的缓存条目，防折扣期
  延长/跨换档的键漂移丢行）
- 卡片**左栏「上次新史低」**（2026-10-09 用户定案改名，原「距上次史低」）：
  平史低 → 主文本 **N 天** = 距上次**同价**时刻（storelow/v2，精确），
  **YYYY-MM-DD 日期走悬停（title）或点按切换**（虚线下划线标记，批 D）；
  新史低 → **N 天** = 距上次**史低期**开始（自有史低期记忆 `game_meta.low_period.prev`，
  2026-10-09 起补上 —— storelow 对新史低返回空，只能自己攒）；记忆未建立
  （该游戏首次史低 / 冷启动）→ 兜底文案 **本次新史低**（无悬停/点按）；
  取不到不渲染该行（不猜）
- **史低期记忆**（2026-10-09）：每个游戏在 `game_meta` 记一对时间戳
  `low_period = {cur, prev}`（史低期**开始**时间），史低首次入账时滚动更新
  （同 start 的续期/重挂不动，免疫折扣期延长键漂移）。冷启动 / 定点回填走
  **通用手动工作流 `backfill.yml`**（`script` 入参选定 `tools/backfill_*.py`），
  当前脚本 `backfill_low_period.py`：**数据源 = ITAD `GET /games/history/v2`**
  （逐条、`shops=61` Steam 口径、`since` 拉长到 ~800 天 —— 默认只回 3 个月不够用，
  实测上一次史低期常在 1~2 年前），从中推「价格 ≤ 此前历史最低」的时刻当史低期；
  **只补「能进列表」的条目**（`classify.is_shown`，冷门不查，省配额）、
  **只填空不覆盖**（已有 `prev` 跳过、`cur` 不回退）、复用 `RateLimiter` 限流
  （逐条 GET，~7.7k 目标 ≈ 50 min）。日常运行自然积累
- 失败不阻断本轮（下次运行自动重取）；run_log 记 `last_low_fetched`

> 因为这些史低**最近才发生**（刚打过新史低），不是 ITAD 历史不够长。

## 4. 判定规则

### 4.1 史低分类（直接用 `flag`）

| 报表标签 | 条件                             | 颜色     |
| ---- | ------------------------------ | ------ |
| 新史低  | `steam_low_class() == "new"`   | 红      |
| 平史低  | `steam_low_class() == "tie"`   | 灰      |
| —    | `flag == None`                 | 不进报表   |

#### ⚠️ 展示口径是 Steam，不是 ITAD（批 E spec E1，2026-09-24）

`deal.flag` 的 N/H/S 是 **ITAD 全商店口径**；本报表只做 Steam，所以页面上的
「新 / 平」由 `classify.steam_low_class()` 自己判，不再直接搬 `flag`：

```
low_kind(deal) is None       -> None       # 不是史低
low_kind(deal) == "unknown"  -> "unknown"
flag == "N"                  -> "new"      # 全网首次 ⇒ 必定 Steam 首次
last_low_at 或 start 缺失     -> "tie"      # 回落 ITAD flag
|last_low_at - start| <= 24h -> "new"      # 店内史低就是这次创下的
否则                          -> "tie"
```

依据是 `storelow/v2` 给的「Steam 店内史低被记录的时间」（§3.6）—— **该接口每天已在跑，
本方案不新增任何请求**。离线验证（51 条，一次性探针，结论沉淀于本表）：
N 9/9 间隔为 0、H 33/33 与 S 9/9 均间隔 ≥37 天；窗口取 1h~72h 结果完全一致。

> 术语：**「店史低」退役**。本页收录的本来全是 Steam 店史低，用它做标签会让人以为
> 还有别的口径。`平史低` = Steam 以前到过这个价（含 ITAD 的 H 与 S）。

交叉校验：若 `flag is None` 但 `price <= storeLow`，记一条异常日志，便于发现 ITAD 口径变化。

### 4.2 当日新增

**主口径：`deal.timestamp`** **的日期 == 运行当天（`Asia/Shanghai`）。**
这一条同时决定了「哪些游戏需要去取详情」。

**兜底口径：本地状态中不存在该** **`(game_id, price, expiry)`** **组合**（首次见到）。
仅在 `timestamp` 缺失或跨时区异常时使用，避免把老折扣误判成新增。

> **为什么主口径必须是** **`timestamp`** **而不是本地状态？**
> 因为 Q18 定了「只补当日新增、历史不补」。如果把「首次见到」当主口径，
> 那么第一次运行会把当前全部 **1228 个史低**都算作新增、全部去取详情——
> 既违背「历史不补」，也会一次性打掉 1200+ 次请求。
> 用 `timestamp` 作主口径，则第一次运行只取「今天开始打折」的那几十\~几百个。

**`--baseline`** **的职责**：只把当前全部折扣**写入状态**（不发详情请求、不产出报表），
目的是让后续运行的「首次见到」兜底规则不误触发。

### 4.3 时区

一律按 **`Asia/Shanghai`** 判定日期。GitHub Actions 的 cron 现已支持 `timezone:` 字段。

### 4.4 多版本去重（同一 Steam appid 的多个条目）

✅ 实测（24 条史低候选 → 21 个 appid）：**存在多版本的 appid 有 2 组、涉及 5 条，
多版本占比约 21%**。去重不是可选项，是必需的。

| appid   | 条目                                                    | 现价       |
| ------- | ----------------------------------------------------- | -------- |
| 447040  | Watch\_Dogs® 2 Gold Edition                           | 19.9     |
| 447040  | Watch\_Dogs® 2 Deluxe Edition                         | 17.4     |
| 447040  | **Watch\_Dogs® 2**                                    | **14.9** |
| 1924170 | TT Isle of Man: Ride on the Edge 3 Racing Fan Edition | 9.9      |
| 1924170 | **TT Isle of Man: Ride on the Edge 3**                | **8.4**  |

**规则：同一 appid 只保留价格最低的那条。**

✅ 为什么用纯数值规则而不用「标题不含版本后缀」：两组样本里，
**「不带版本后缀」的那条恰好就是「价格最低」的那条**——带后缀的版本含 DLC 包，
通常更贵。两个判据结果一致，那就选**不需要解析标题、更稳健**的那个。

> 把被合并掉的条目连同标题写进 run\_log，便于事后核对是否误合并。
> 「在详情页里列出同游戏其他版本的价格」是可选增强，实现成本高则砍掉。

> 注：本节规则**不能**用来省 `info/v2` 请求——必须先调 `info/v2` 才知道 appid。
> 它的收益是报表不重复展示，以及**减少 Steam 跨区批量请求**（每个 appid 只查一次）。

### 4.5 过期与留存

- 展开中的折扣：`expiry > now`
- 即将过期：`0 < expiry - now <= 48h`
- 已过期：`expiry <= now`
- **折扣过期后再保留 7 天**再删除（应对「隔几天又打折」的情况）
- 不保留每日页面快照——需要回溯往日价格时直接查 ITAD 的 `games/history/v2`

### 4.6 视图窗口

| 视图   | 定义                                              | 状态 |
| ---- | ----------------------------------------------- | ---- |
| 当日新增 | `timestamp` 的日期 = 今天（Asia/Shanghai）             | 已上线（S9 起以首页「新史低」板块 + 顶部摘要呈现，不再是独立视图） |
| 本周   | `timestamp` 落在「本周一 00:00 \~ 下周日 23:59:59」（14 天） | 已上线（2026-10-05 S5，`all.js` 懒加载） |
| 折扣中  | `expiry > now`                                  | 已上线（2026-10-05 S5，`all.js` 懒加载） |
| 即将过期 | 距 `expiry` 不足 48 小时                             | 已上线（2026-09-27 批 H） |

> **「已过期」（`expiry <= now`）已从视图里删除**（批 F2）：折扣过期后对买家毫无浏览价值
> （用户原话「过期折扣犹如砒霜」）。`classify.is_expired()` 与
> `expired_retention_days`（过期后留 7 天再清理）**都保留** —— 留存清理仍要用；
> 但 `classify.VIEW_KEYS` 里不再有它，`in_view("expired", …)` 会抛 `ValueError`。

窗口一律按**折扣开始时间** `timestamp` 分组；状态一律按 `expiry` 判定。
**所有视图都先过「史低」这道门**——非史低的普通折扣不进报表。

- **池子**：折扣开始 ≤ `home_new_low_days`（7）· 还在折扣期内 · 史低类型 ∈ {新史低, 平史低}，
  **按顺序逐层取**（优先新史低，不够才补平史低）。

  ⚠️ **表里不许出现「史低类型」项**（有单测锁定）。
  ⚠️ **「间隔」的覆盖（2026-10-09 起）**：平史低 = 距上次同价（ITAD storelow），
  新史低 = 距上次史低期（自有记忆 `low_period.prev`，见 §3.6）；记忆未建立时无值
  → 该项不计分。冷启动阶段新史低卡间隔大面积为空属预期，随史低期轮转渐进补齐。
  ⚠️ 2026-10-09 之前大卡与「新史低」板块共用同一套权重，同一批新史低池排出的
  **条目和顺序完全一样**（大卡 = 板块前 15 名复读，用户指出）—— 两处语义不同：
  板块是「今天有什么新史低」的榜单（名气优先，见 §7.3），大卡是「今日最值」门面位
  （折扣优先），故拆成两套权重档。
- **形态**：白底；封面 3:4（三档统一，避免断点跳）；左上排名徽章；底部署低类型色条（新红 / 平灰）；

  无比价数据时右栏写一行说明（不回落单栏）。**比价现查只覆盖「当日新增 + 即将到期」**，
  其余历史条目为估算（外区原价缓存 × 国区折扣比例，`enrich.estimate_compare`，
  口径见 `CONTEXT.md`「现查与估算的分工」）。
- **点大卡 → 跳「新史低」板块 + 自动定位并展开那一行**（2026-10-09 用户定案 A；
  原来只跳转，用户「不能一眼找到刚才点击的大卡详情」）：大卡点击记下 `game_id`，
  落地后按 `.row[data-gid]` 命中就滚动 + 展开；还没渲染到就**一次加载到位**再定位
  （分片有缓存，代价有限）。
- 缺详情的行显示「**详情待补**」，不影响浏览，下次运行自动补上。
- **好评率 / 剩余天数分档上色**（服务端 `report.rate_tier` / `days_tier`），前端只拼 span。

#### 7.3.1 板块完整列表的数据：按板块顺序分片（2026-10-08）

- 板块完整列表（点「查看更多」进去那张页）的数据**不再是一个 `all.js`**，而是
  `all/<板块>_<片号>.js`，每片 200 条（`ALL_SHARD_SIZE`），由 `report.write_all_shards` 产出。
- **为什么必须按板块各自顺序切片**：试过「共享池分片 + 板块索引」，池顺序（tier 分组 +
  折扣降序）跟板块排序不相关，实测「热门游戏」前 30 条散落在 18 个分片里，等于没优化。
  代价是卡片在板块间重复存储（发布体积 5.8MB → 13.1MB raw），属可重建产物，认了。
- **顺序 = 分片的物理顺序**（片号 0,1,2… 依次读出来就是板块顺序），所以服务端不再
  单独下发 `section_order`；排序口径仍然只有服务端一份（`report._section_sort`）。
- **第 0 片额外带** `total` / `shards` / `size` / `agg`：
  - `agg` = 构建期算好的**预聚合计数表**（5 个板块 × 160 个筛选组合的精确条数，约 4KB raw）
    ⇒ **只加载第 0 片也能显示精确的「共 N 条」**，筛选不必退化成全量加载。
  - ⚠️ `agg` 的判据必须与 app.js 的 `dateOk` / `filterOk` / `liveOk` 同一口径，
    且 `report.filter_dim_values` 与 `report.filter_specs` 的选项必须逐项一致（有单测锁）。
- 前端：`window.ALL_S["<板块>_<片号>"]` + `loadShard()`，仍是**动态 `<script>`** 而不是 fetch
  （`file://` 直开要能用）；按已加载部分的命中率外推再取几片，`SHARD_CONCURRENCY = 4`。
- **换「折扣 / 价格 / 好评」排序 = 全局重排**，必须拿到该板块全部分片 ⇒ 并发全取
  （代价与改动前点一次分类相同，属次要路径）。实测另一份「列式排序键」只能在这条路径上
  再省约 40%，却要在 app.js 复制一份筛选判据 —— 与「判据只有一份」冲突，不做。
- **首页空闲预取**：`requestIdleCallback` 串行偷跑五个板块的第 0 片（≈100KB）。
  用户已经进了某个板块就立刻停手。不划算就把 `prefetchShards` 那段删掉，
  分类页仍然只比现在快 33 倍。
- ✅ **实测**（线上 7276 张卡片）：首片 gzip `new_low` 19.8KB / `expiring` 18.2KB /
  `popular` 21.8KB / `big_cut` 18.6KB / `__all__` 19.4KB —— **降幅 97%**；构建 0.5s。
- ⚠️ 发布时 `output/all/` 会先被清空再写（池量每天变，防昨天的旧分片一起发布）。

### 7.4 视觉规范（决策层；具体值以 `app.css` 变量为准）

- **颜色语义（一个色相只干一件事）**：红 = 价格上的好消息（新史低色条 / 现价**同号**）、
  深一档红 = 比价「贵」；绿 = 折扣力度（条与百分比同色）；蓝 = 主色 / 好评率（**单蓝号**，≥90 只加粗）；
  粉 = 「今天结束」（粉底 + 白字）；琥珀 = 警示（剩余天数紧迫 / 口碑偏低）。
  ⚠️ **别让「新史低」变绿**（会跟「折扣力度」串味）。
- **字号 6 档**（`--fs-aux/sub/body/price/title/brand`）、**间距 5 档**（`--sp-1..5`）；
  容器 max-width **1200px**、留白 `clamp(12px,4vw,56px)`。
- **断点两档**：手机 ≤600 / 平板·PC 601~1100 / PC ≥1101（`mobile_breakpoint_px` /
  `tablet_breakpoint_px` 经 `payload.list` 下发；**改值必须同步 CSS `@media`**，有机械校验断言）。
- **空状态**三态（无内容 / 加载中 / 加载失败）用**自绘内联 SVG**（不引图片文件），
  配色用站点现有色；失败态带「重试」按钮。

### 7.5 双端适配

- **不做 UA 判断**，一套响应式 CSS（UA 已不可靠：iPad 报 macOS、浏览器有「桌面版」开关；
  而 UA 判错的后果是布局崩，`@media` 不会错）。
- 手机上：导航收成汉堡、筛选按钮进右下浮层、精简/返回顶部做成浮动按钮（返回顶部滚动 >400px 才出现）。
- **精简模式**（`body.compact`）：封面隐藏、中英名同行、间距收紧、力度条下移一行；
  状态存 `localStorage`（初始化只应用不回写）。
- 移动端贴合安卓习惯：不做右上角小 × 按钮。

### 7.6 其他

- **PWA：不做**（明确砍掉）；**搜索引擎收录：无所谓**，不加 noindex。
- 页脚：链接 + 一句话说明 + 免责，**居中**；**不含生成时间 / 最近运行时间**（那些在顶栏与 about 页）。

### S8 工作流加固（2026-10，spec §3.6「S8 修订」）

- **timeout-minutes**：主跑 90 · 预抓 60 · guard 5 · 清理 10 · 告警 5（此前吃默认 360 分钟）
- **失败自动开 Issue**：`alert` job 监听各 job failure（cancelled 不告警，有意——
  取消是人主动行为或已被 timeout 说明），正文附 run.py 退出码。退出码口径：
  0 成功 · 1 未预期 · 2 配置 · 3 滥用封禁 · 4 请求失败（**仅报表产出前**，页面没更新）·
  **5 详情/覆盖阶段失败**（含请求失败；页面已兜底发布首版，欠账下轮自愈）——
  4/5 的判别轴是「页面是否兜底」，不是异常类型（review-s8 P1-1）
- **`$GITHUB_STEP_SUMMARY`**：每轮一张关键指标表 + 阶段墙钟（run.py 写入）
- **报表发布韧性**：「打包报表 / 发布 Pages」`if: !cancelled()` + `hashFiles` 兜底——
  run.py 退出码 5 时首版报表照常发布，页面永远可见；手动取消 / 超时连带取消时
  不发布半成品；失败 run 不计 guard 的「成功定时 daily」，补跑照常重试详情，
  成功后完整版覆盖。状态回写仍用 `always()`：取消场景下已抓一半的状态写回去，
  下一轮断点续传受益
- **permissions 按 job 最小化**（顶层清零）；data 回写 push 前 `git pull --rebase`
- daily/prefetch 的状态恢复与回写重复块抽成 `.github/actions/{state-restore,data-writeback}`
- actions 全升当前主版本（checkout@v7 / setup-python@v7 / configure-pages@v6 /
  upload-pages-artifact@v5 / deploy-pages@v5 / upload-artifact@v7；Node 20 已于
  2026-09-23 退役）；`ubuntu-latest` 维持（10-19~11-19 渐进迁 Ubuntu 26.04，观察首跑）
- **`backfill.yml` + `tools/backfill_queue.py` + `.scratch/backfill-autumn-2026/uuids.jsonl`
  已删除**：S2 派生欠账管线使「大促永久欠账」机制性消失，回填手术刀无二次价值

### 三个必须处理的坑（都来自官方文档核实）

1. **`GITHUB_TOKEN`** **推送的 commit 不会触发 Pages 构建**（官方防递归）
   → 发布**必须**用 `actions/deploy-pages` 在**同一次运行内**完成，不能靠「部署自分支」
2. **公开仓库 60 天无活动会禁用定时任务** → 每日提交状态文件正好算作仓库活动，顺带规避
3. **Actions runner 无持久磁盘** → 靠 `GITHUB_TOKEN` 把状态 JSON 提交回仓库
   （`actions/cache` 有 7 天淘汰规则、官方明确不能当可靠存储；artifact 只留 90 天）
4. **`.gitignore`** **必须写成** **`data/*`** **+** **`!data/state.json`，不能写** **`data/`。**
   实测（临时仓库里跑 `git add -A --dry-run`）：
   | 写法                            | 实际会暂存的内容                                                 |
   | ----------------------------- | -------------------------------------------------------- |
   | `data/`                       | `.gitignore`、`run.py` —— **`data/state.json`** **被静默跳过** |
   | `data/*`（漏了取反）                | 同上，仍跳过                                                   |
   | `data/*` + `!data/state.json` | `.gitignore`、**`data/state.json`**、`run.py` ✅            |
   写成 `data/` 时 git 根本不会进入该目录，后面的 `!` 取反是无效的。
   后果非常隐蔽：**本地跑完全正常**，只有 Actions 上每轮都从空状态开始
   （详情缓存全失效、`game_meta` 的 TTL 形同虚设），而坑 2 的「每日提交算作仓库活动」
   也一起失效。

> 前置：本仓库目前**尚未** **`git init`**（工作区里没有 `.git`）。
> 第 9 步之前要先建仓库、加 remote、确认 `.gitignore` 生效。

### 缓存与刷新

- Pages 有约 10 分钟缓存，**且不支持自定义响应头**
  → 资源加 `?v=<生成时间戳>`，页面内显示生成时间以便区分新旧

### 失败告警（两层）

1. GitHub 通知设置里开启 Actions 的「仅失败时通知」（用户级设置，不用改 workflow）
2. 页面内建**数据陈旧横幅**——即使通知被忽略，一打开页面就知道数据是旧的

## 10. 错误处理

- **五种响应分开处理**（不能都当成"限流"）：
  | 响应                       | 处理                                               |
  | ------------------------ | ------------------------------------------------ |
  | `429`                    | 尊重 `Retry-After`；没有则从 10 秒起退避，逐步加到分钟级；同时**自动降速** |
  | `403`                    | 比 429 严重（滥用封禁）。等 5 分钟后重试；**连续出现则中止本轮并告警**        |
  | `200` 但 body 是字面量 `null` | 软限流。按限流处理，**绝不能当成"没数据"**                         |
  | `200` 且 `success: false` | 不是限流：appid 不存在 / 该区不售。记 run\_log 后跳过             |
  | `503`                    | 服务端故障，与限流无关。重试，**不计入限流统计**                       |
- **绝不轮换 IP 规避限流**（社区明确不建议，长期会导致密钥/IP 封禁）
- **退避重试**：5xx 指数退避 + 抖动；网络异常重试 3 次
- **断点续传**：详情抓取按 uuid 逐条落盘，中途失败下次只补缺的，不从头再来
- **部分失败不阻断**：单个游戏取详情失败 → 该条标记「详情待补」，不中断整轮
- **幂等**：状态键含 `(game_id, price, expiry)`，同日多次运行不产生重复数据
- **异常数据如实记录**：`storeLow` 缺失 → 标记 `unknown`、**不列入史低**但单独计数，
  不把「数据缺失」静默当成「不是史低」；各过滤条件砍掉的条数逐项记入 run\_log
