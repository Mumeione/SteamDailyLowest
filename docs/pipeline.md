# 抓取流程与请求预算

> 描述主跑 / 预抓的流水线、筛选链规模、请求预算与缓存策略。
> 数据源能力与实测细节见 [data-sources.md](data-sources.md)；
> 判定规则见 [domain-rules.md](domain-rules.md)；
> 状态库结构见 [data-model.md](data-model.md)。
> 各参数默认值见 [config-reference.md](config-reference.md)，以 `config.py` / `config.example.json` 为准。

## 运行模式

| 模式 | 触发 | 干什么 | 出报表 |
| --- | --- | --- | --- |
| 默认（daily 主跑/补跑） | Actions 定时 | 全流程：抓列表 → 筛 → 详情 → 比价 → 报表 → 快照 | ✅ |
| `--baseline` | 手动 | 只翻页抓列表写入状态，**不取详情**（让「首次见到」兜底不误触发） | ❌ |
| `--audit` | 手动 | 无 filter 全量翻页（162 页），保住 `type`/`flag` 全分布与交叉校验 | ✅ |
| `--prefetch` | Actions 定时 | 只补状态库派生的详情欠账，**不扫描折扣列表** | ❌ |
| `--probe` | 手动 | 从状态库抽 3 个游戏实时重拉与缓存对照，报告写 `output/probe_report.txt` | ❌（写探针报告） |

## 流水线

```
① 抓折扣列表        ② 筛选链             ③ 判史低        ④ 判当日新增
   GET /deals/v2  →  type==game      →   flag != None  →   timestamp=今天
   （国区，翻页）     排除免费             （N/H/S）        （主口径，
                      折扣阈值                              本地状态仅兜底）
                                                              ↓
                    ⑦ 报表输出        ←  ⑥ 跨区比价      ←  ⑤ 取详情（派生式欠账）
                       index.html +      Steam appdetails    GetItems 批量（主源）
                       data.js +         appids 批量         info/v2 逐条降级
                       latest.json +     cc=ua/in/cn
                       all/ 分片 +
                       expiring.json
```

**先渲染后覆盖**：详情抓取**之前**渲染一版首版报表（缺的标「详情待补」），
抓完**之后**覆盖同一份产物（两次共用同一个 `now`，页面生成时间与 `?v=` 不跳动）。
渲染核心（`render_pass()` / `merge_details` / `build_stats` / `count_backlog`）
住在 `src/pipeline.py`，`run.py` 只编排——零网络的渲染工具（`tools/render_report.py`）
因此不必 import 入口 module。

## 筛选链与各步规模（实测）

抓取口径（`sweep_mode`）决定「从全量开始筛」还是「让服务端先筛掉」：

| 口径 | `/deals/v2` 请求 | 拿到的条目 | 说明 |
| --- | --- | --- | --- |
| `low_only`（**默认**） | **27 页** | 5,243（本体 + 史低） | `filter={"type":[1],"flag":"S"}`，见 [data-sources.md](data-sources.md) |
| `full`（`--audit`） | **162 页** | 32,364（全部折扣） | 无 filter，用于体检与交叉校验 |

`low_only` 口径下的筛选链（**实测，国区 2026-09-21**）：

| 步骤 | 条件 | 剩余规模 |
| --- | --- | --- |
| 抓取（服务端已过滤） | `type=[1]` + `flag=S` | **5,243** |
| 排除免费 | `price > 0` | ~5,240 |
| 判史低（服务端给的是超集） | `flag != None` | **5,243**（与实际 5,246 之差为数据抖动） |
| 当日新增 | `timestamp` = 今天 或 本地首次见到 | **实测 105~106 条** |
| 取详情 | 派生欠账里缓存未命中的 | 首轮 105 → 之后每天几十~几百 |
| 好评过滤分档 | 见 [domain-rules.md](domain-rules.md) | **进列表约 20 条**（106 个新增里） |

`full` 口径下（体检用）能额外得到：
本体 9,535 · 非本体 22,829 · 非史低 4,286 · `flag` 分布 N=1,224 / H=3,310 / S=712。

> ⚠️ `low_only` 口径下 `type_not_game` / `not_historical_low` / `flag_price_mismatch`
> 三个计数**必然为 0** —— 那不是「今天没有异常」，而是这两个口径看不到，
> 必须在 `run_log` 里连同 `sweep` 一起记录，否则会被误读。
> 每一步「砍掉多少条」都要写进 `run_log`，便于按真实数字调阈值。

## 详情管线：派生式欠账

**目标 = 当日新增 ∪ 折扣活跃且数据年龄超 TTL ∪ unlisted 重判**（预抓额外含「只缺中文名」），
**不设条数预算**；命中缓存的直接跳过。三跳：

1. 缺 appid 的 uuid → `lookup/shop/61/id/v1` 批量映射（免鉴权、不计额度）；
2. 有 appid 的 → **GetItems 批量**（250/批）：好评率 + 厂商 + 中文名 + 封面一次到手，
   每批落盘一次，**连续 3 批失败即熔断**（本轮剩余批次全部降级）；
3. 前两步拿不到的 → `info/v2` 逐条降级（完整 ITAD 口径），每轮上限
   `detail_fallback_budget`（默认 1000）—— 降级 1 请求/条，必须设界；
   GetItems 正常时该路径平时为空。

写完 `seen_deal` **立刻 `save()`**——否则一旦详情全部失败，这一轮 5000 多条攒库会被一起丢掉。

**「越跑越全」是天然成立的**：某个游戏只要**下一次重新打折**，它就会重新进入
「当日新增」，那一刻自然抓到详情并写进缓存。不存在「永远补不上」，只是补齐时机
取决于该游戏下次打折的时间。

## 请求预算

**关键约束：`info/v2` 一游戏一请求、没有批量端点。** ✅ 已实测确认：
`POST /games/info/v2` 返回 **405**；`POST /games/overview/v2` 虽能批量但不含
`appid` 和 `reviews`，替代不了。所以「appid + 好评率」逐游戏取的成本无法消除，
但 GetItems 批量（250/批）已把它压到日常几十~几百次/轮。

### ⚠️ 大促爆发：一天几千条史低怎么办

实测过：单次大促首日，「当日新增」可能等于全部史低候选（**几千条**）。
**结论：这仍然可行，限流不是障碍，关键是节流方式。**

- ITAD 的 **1000 请求 / 5 分钟是「速率限制」，不是每日配额** ——
  每天总请求量**没有上限**，只要节流得当，多抓几千条完全可行
- 3000 个详情 ≈ 3 个限流窗口；**约 20 分钟抓完**
- 一天两次运行（主跑 03:14 + 补跑 05:21，北京时间），时间上完全宽裕

必须做的三件事：

1. **限流三管齐下**（滑动窗口 + 最小间隔 + 串行），参数见
   [config-reference.md](config-reference.md)。⚠️ **必须同时限制并发数**：
   持续高并发本身就会触发 429，把并发压到 1（串行）最省心。
   遇到 429/403 就**自动降速**并把事件写进 run_log——这是唯一需要的「被动调参」依据，
   **不需要主动去探顶**。
2. **报表与详情解耦：报表永远不等详情。** 首版先发布，页面立刻可看（见上文「先渲染后覆盖」）。
3. **断点续传 + 优先级。** 详情按 uuid 逐条落盘，优先抓「当日新增」，
   抓不完的下次运行接着抓（缓存命中自动跳过）。

### 各阶段请求构成

| 阶段 | 请求构成 | 量级 |
| --- | --- | --- |
| 首次 `--baseline` | 只翻页抓列表写入状态，不取详情 | 20~27 次（`full` 口径 162） |
| 日常主跑 | 翻页列表 + 详情目标全部抓 | **27 + 目标数（通常几十~几百）** |
| 预抓 `--prefetch` | 纯 state 派生欠账，预算 `prefetch_daily_budget`（默认 300，`0` = 关闭） | ≤300 |
| 上次史低时间 | `storelow/v2` 批量（200 个/批） | 日常约 1~10 次/天 |
| 中文名（逐游戏补名） | Steam 单请求、**永久缓存**，只有从没见过的才发 | ≈ 当天新增缺名数 |
| 跨区比价 | Steam `appdetails` 批量（20 个/批），每区 1 组，**不占 ITAD 配额** | 进列表 appid ÷ 20 × 区数（UA + IN） |

> ⚠️ **试过用服务端 `filter={"steamCount":{"min":100}}` 先筛掉冷门，被否掉**：
> ITAD 对相当一部分游戏**根本没有 Steam 评测数据**（实测当日新增里 39/107 条拿不到好评率），
> 拿它当门槛会**静默丢掉 Steam 上其实评价很多的游戏**。宁可多花请求，
> 也要让客户端拿到全量后自己判档。

## 缓存策略

| 数据 | 生命周期 | 说明 |
| --- | --- | --- |
| `appid` | **永久** | Steam AppID 不会变 |
| `reviews` | **折扣感知四档 TTL**：新游（发行 ≤`new_game_days`）1 天 / 到期窗口（expiry − `upcoming_expiry_hours` 起）1 天 / 折扣活跃期普通条目 3 天 / **非折扣期不刷新**（无消费方） | 刷新节奏由条目状态决定，不设全局 TTL |
| `title_zh`（中文名） | **永久**，与 `reviews` 是**两条独立缓存** | `set_title_zh()` 不碰 `fetched_at`，否则会把好评率的 TTL 一起刷掉 |
| `cover`（Steam 封面补缺） | **永久** | 只为「ITAD 无 boxart」的条目落库 |
| `compare_cache` | **永久**（键 `<appid>|<cc>`，存区域**原价** `initial`） | 不随折扣期失效、**不参与留存清理**（键不含 expiry）；现价（`final`）每轮对进列表条目**真查**（当日新增 + 即将到期合并去重，20 个/批），真查响应里的原价与缓存比对——不一致即 Valve 区域重定价，回写自愈并记日志（「真查即校准」）。整区真查失败时该区该轮缺行（不回落，下轮自愈）。⚠️ 缓存丢失后历史 appid 的原价**无法重拉重建**，只能靠 data 分支 git 历史找回 |
| `low_time_cache` | **折扣期暂存**（键 `<game_id>|<expiry>`） | 随 `cleanup_expired` 与 `seen_deal` 同保留期清理；精确键 miss 时回退到该游戏折扣期最新的缓存条目（防折扣期延长/跨换档的键漂移丢行） |
| `heybox_miss` | 负缓存，TTL 90 天 | 小黑盒也没有译名的条目期内不重查，到期自动重查自愈 |

比价的「现查与估算分工」口径见 [../CONTEXT.md](../CONTEXT.md) 的同名词条：
真查只覆盖「当日新增 + 即将到期」，其余历史条目用估算
（`enrich.estimate_compare` 单一出处）——**原价永久缓存就是为估算备料**。

## 上一次史低时间

`POST /games/storelow/v2`（body 为 uuid 数组，带 `country` + `shops`）返回每个游戏的
商店历史最低价，**并且带 `lows[].timestamp` = 该最低价被记录的时间**。

- **批量接口**（200 个 id/次）→ 日常约 1~10 次请求/天，几乎不增加请求量
- 解读方式（结合 `flag`）：

| flag | `lowest.timestamp` 的含义 |
| --- | --- |
| `N`（新史低） | 时间戳 ≈ 本次折扣开始时间 → **正是这次破的记录** |
| `H`（平史低） | 时间戳更早 → 就是**上一次达到史低的时间** |
| `S`（仅店史低） | 同上，但另有商店更便宜过 |

落地口径（`run.fetch_last_low_times` + `ItadClient.fetch_storelow`）：

- 对**当日新增 + 即将过期候选**取（即将过期条目大多从未当过当日新增，没有该字段），
  每轮**整批重取**不做缓存跳过 —— 否则游戏再次新低时会拿过期时间；
- 存 `low_time_cache`（键 `<game_id>|<expiry>`，同一游戏多版本折扣各存一份）；
- 卡片**左栏「上次新史低」**：平史低 → 主文本 **N 天** = 距上次**同价**时刻
  （storelow，精确），日期走悬停（title）或点按切换（虚线下划线标记）；
  新史低 → **N 天** = 距上次**史低期**开始（自有记忆 `game_meta.low_period.prev`——
  storelow 对新史低返回空，只能自己攒）；记忆未建立 → 兜底文案**本次新史低**；
  取不到不渲染该行（不猜）
- **史低期记忆**：每个游戏在 `game_meta` 记一对时间戳 `low_period = {cur, prev}`
  （史低期**开始**时间），史低首次入账时滚动更新（同 start 的续期/重挂不动，
  免疫折扣期延长键漂移）。冷启动 / 定点回填走通用手动工作流 `backfill.yml`
  （`script` 入参选定 `tools/backfill_*.py`）：当前脚本 `backfill_low_period.py`
  数据源 = ITAD `GET /games/history/v2`（逐条、`shops=61`、`since` 拉到 ~800 天，
  默认只回 3 个月不够用——上一次史低期常在 1~2 年前），从中推「价格 ≤ 此前历史最低」
  的时刻当史低期；**只补「能进列表」的条目**、**只填空不覆盖**、复用 `RateLimiter` 限流。
  日常运行自然积累
- 失败不阻断本轮（下次运行自动重取）；run_log 记 `last_low_fetched`

> 它同时回答了「`historyLow == historyLow_1y` 比例为何极高」：
> 因为这些史低**最近才发生**（刚打过新史低），不是 ITAD 历史不够长
> （实测：H 组 71/72、N 组 27/28 满足相等）。

## 设计不变量

改动代码时不得破坏这些性质（原验收标准中的结构不变量，永久现役）：

1. **状态库幂等**：同一天重复运行，同一 `(game_id, price_int, expiry)` 只写一条，
   `first_seen_at` 不被覆盖。⚠️ 不要用「当日新增数量不变」来验证——主口径是
   `timestamp`、每轮从实时数据重算，期间有新折扣上线数量就会变。
2. **状态先落盘**：写完 `seen_deal` 立刻 `save()`，详情一条都没抓成时 `seen_deal` 依然完整写入。
3. **报表与详情解耦**：详情阶段被打断（强杀进程）后，`index.html` 仍然存在，
   缺详情的条目标「详情待补」。
4. **断点续传**：详情按 uuid 逐条落盘，中途失败重跑只补缺失的，不重复请求已有的。
5. **部分失败不阻断**：单个游戏取详情失败 → 该条标记「详情待补」，不中断整轮。
6. **幂等缓存命中不发请求**：缓存命中直接跳过，这是把请求量压下来的关键。
7. **多版本去重**：同一 appid 只出现一次，保留价格最低的那条（判据见
   [domain-rules.md](domain-rules.md)）。
8. **run_log 完整性**：各过滤条件砍掉的条数、limiter 统计逐项入 run_log。
